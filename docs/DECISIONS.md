# Implementation decisions

Material choices made while implementing `MVP.md`, with the reasoning. Product scope was not changed; these fill gaps or pick among allowed options. Requirement IDs refer to the acceptance matrix in `MVP.md`.

## Toolchain and versions

| Decision | Rationale |
| --- | --- |
| Node 22.22.0, pnpm 10.28.0, Nx 23.2.1 (integrated `project.json` layout), TypeScript 5.9.3 | Mutually compatible stable set verified against npm peer ranges on 7 Oct 2026. Angular 22 needs TypeScript 6 and a newer Node patch; NestJS 12 is outside the Nx 23 support range. |
| Angular 21.2 (standalone, zoneless, signals) + Angular Material 21.2 with the M3 `mat.theme` API | Default UI library per `AGENTS.md`; zoneless is the Angular 21 default. Icons are inline SVG paths registered in `MatIconRegistry`, and fonts use the system stack, so the dashboard has no CDN dependency and works offline in Docker. |
| NestJS 11.2 with Zod (`nestjs-zod` kept only as a dependency; validation runs through a small `zodBody` pipe) | Contracts are Zod schemas shared by API and UI (`libs/contracts`), giving one source of truth for limits and DTOs. |
| Prisma 7.10 with the `prisma-client` generator and `@prisma/adapter-pg` | Prisma 7 requires a driver adapter; generated client is git-ignored and regenerated by `pnpm db:generate`. |
| Jest 30 (unit + integration), Playwright 1.63 (critical journeys), ESLint 10 flat config | Required by the specification. Integration tests run against a real PostgreSQL database (`TEST_DATABASE_URL`) with migrations applied by a global setup. |
| XLSX handled by a small in-repo reader/writer on `fflate` + `fast-xml-parser` | The npm `xlsx` package has unpatched advisories and `exceljs` is unmaintained; the subset Raaye needs (inline strings, numbers, formulas detection) is small and fully tested. |
| `libphonenumber-js/max` for phone normalization | Required for correct E.164 handling of Pakistani and international numbers. |
| No `whatsapp` Node SDK | A typed `fetch` adapter (`meta.provider.ts`) keeps payloads explicit and testable. |

## Architecture

- **Three libraries, three apps.** `libs/contracts` (schemas and DTOs), `libs/domain` (pure rules: edit windows, consent derivation, selection validation, aggregates, CSV/XLSX, phone, copy), `libs/server` (NestJS modules, persistence, jobs, messaging, conversation engine, reporting, seed). `apps/api` is thin controllers, `apps/worker` runs the job loop and CLI commands, `apps/web` is the dashboard.
- **Tenant scoping by construction.** `createTenantDb(prisma, organizationId)` is a Prisma `$extends` client that injects `organizationId` into every `where`, `data`, `create` and `upsert` of every tenant-owned model and refuses control-plane models (`User`, `WebhookQuarantine`, `SimulatorState`). Controllers and domain modules receive the scoped client through `TenantDbFactory`. The unscoped `PrismaService` is used only by control-plane code that has no tenant yet or is cross-tenant by nature: membership resolution, staff-invitation inspection and acceptance and the `bootstrap:org` command, webhook connection mapping and inbox persistence and quarantine, due-job claims and the sweep's cross-tenant due-run discovery, retention sweeps, user lookups for display emails, simulator state, the health probe and seed. `AuditService` builds its own scoped client from it with `createTenantDb`. Composite foreign keys `(organization_id, parent_id)` make cross-tenant relation connects impossible at the database level (R07, R08).
- **Durable PostgreSQL jobs.** One `jobs` table with `FOR UPDATE SKIP LOCKED` claims, leases, bounded retries with jittered exponential backoff, priorities (opt-outs first) and dedupe keys. The same handlers run in the worker loop, in `POST /api/v1/internal/jobs/:id/execute` (Cloud Tasks) and in the simulator "drain" button. Under `JOB_DRIVER=cloud_tasks` every pending job is pushed to the queue (`pushed_at` tracks the hand-off; retries and recovered leases are pushed again) immediately after enqueue and on each sweep. Deadlines (activation, closing, edit windows) are persisted, never kept in memory (R25-R27, R33).
- **Provider-neutral messages.** The planner produces `RenderedMessage` values (text, buttons, list, flow, template); adapters translate them. The mock adapter injects faults from persisted simulator state; the Meta adapter classifies HTTP errors into retryable/permanent/unknown. A timed-out send is recorded as `UNKNOWN` and never retried automatically (R43).
- **Conversation engine.** One transaction per inbound event; explicit action bindings (opaque tokens) route replies to the exact participation/question; commands (`STOP` has precedence) are parsed before question processing; foreground/background participation state is persisted so switching surveys never cross-wires answers (R15-R22, R31-R42).
- **Answers.** One canonical `answers` row per participation/question plus `answer_revisions` and `answer_selections`; the first accepted answer fixes `edit_expires_at = min(first + window, closes_at)`; row locks on the participation serialize concurrent replies (R31-R35).
- **Reporting.** Aggregates are computed from current canonical selections with explicit denominators (valid respondents; delivery-evidence intersection for response rate). Demographic breakdowns use the analysis profile frozen at the participation's first accepted answer; cohorts under 5 respondents are suppressed for non-Admins (R46-R49).
- **Result sharing.** Admin-only after closure. One frozen aggregate snapshot per run, one broadcast, questions with fewer than 5 respondents withheld, template outside the 24-hour window, `View results` delivers the bound snapshot (R51-R54).

## Defaults and policies chosen

| Topic | Choice |
| --- | --- |
| Edit window | 120 s from the first accepted answer, never reset by edits, capped at survey close, 0 disables (R34-R35). Strictly less-than comparison at expiry. |
| Duration | 48 h from the *intended* opening time; range 1 h – 30 d. Explicit closing instant allowed for Admins. |
| Audience freeze | At scheduling/launch; permission is rechecked by the send policy gate immediately before every send (R24, R45). |
| Imports | Name and phone required; imported rows create contacts with **unknown** permission unless the staff member records a consent attestation for the file. Withdrawn contacts are never re-enabled by an import (R12, R14). |
| Contact uniqueness | Organization + normalized E.164. The same number may exist in two organizations with separate consent (R08). |
| Participant-initiated enrollment | Unknown senders get an enrollment prompt; permission is only granted after an affirmative reply; replies never authorize future campaigns by themselves (R16-R17). |
| Service window | 24 h from the last verified inbound message. Free-form messages outside it are not sent; templates are used for invitations and results notices only (R45, R52). |
| Renderer routing | ≤3 short options → reply buttons; ≤10 → list; otherwise a single-choice Flow. Multiple selection always uses a Flow; ratings use a list 1-5 with optional endpoint labels (R20-R21). |
| Cohort threshold / share minimum | 5 respondents for both, documented as disclosure controls, not anonymity guarantees. |
| Export formula neutralization | Cells beginning with `=`, `@`, tab, CR or LF, with `+` or `-` unless the whole value is a plain signed number or phone pattern (so E.164 numbers such as `+923001234567` and values such as `-15` are left as they are), or with leading whitespace followed by one of `= @ + -`, are prefixed with `'`. XLSX string cells are written as inline text so phone numbers stay text (R50). |
| Retention | Raw import bytes 24 h, raw webhook payloads 7 d, quarantine 7 d, action bindings expire after 45 d (earlier on opt-out, run closure or share revocation) and the row is deleted 30 d after expiry (about 75 d after creation); cleanup runs hourly from the sweep (R56). |
| Audit | Sensitive reads/exports/consent/retry/configuration changes are audited without personal data or selected answers (R06, R49). |
| Demo accounts | `admin@pilap.demo`, `manager@pilap.demo`, `viewer@pilap.demo` plus a second tenant `admin@lcf.demo`. Created only when `ALLOW_DEMO_BOOTSTRAP=true`, which the configuration rejects in live/production mode (R57). |
| Synthetic contacts | Seeded contacts carry `is_synthetic`; the live send policy refuses them unconditionally (R57). |
| Disabled connection | Readiness reports `CONNECTION_DISABLED` for a disabled sender in mock and live mode; launches, test runs, result broadcasts and simulated inbound traffic are refused, signed webhook batches are quarantined with that reason, and the send policy gate suppresses already queued messages with the same reason until an Admin re-enables the connection and retries them explicitly. |
| Sender provisioning | The first **Settings → Messaging** save creates the organization's connection for the configured mode (`META`/`LIVE` with app key `live-<slug>-<random>`, or `MOCK`/`MOCK` with `mock-<slug>`, the key the seed uses) under an organization row lock; readiness reports `CONNECTION_MISSING` until then. Mode, provider and app key are never client-supplied. |
| First-organization bootstrap | `bootstrap:org --name --slug --admin-email` (worker CLI) creates the organization with a placeholder participant notice and issues a single-use 72-hour Admin invitation that has no inviting user (`staff_invitations.invited_by_user_id` is nullable for this case only); acceptance runs through the normal invitation flow, so identity, email, expiry and single use are verified in one place. The command works in live configuration without `ALLOW_DEMO_BOOTSTRAP`, refuses an organization that already has an active Admin, revokes every pending bootstrap link of the organization when re-run (so a corrected address leaves no earlier link alive), records an `organization.bootstrapped` audit event and prints the link once to stdout, never to the structured log (issue #13). |
| Webhook secret resolution | `lookupSecret` resolves a connection's bound `appSecretRef` / `verifyTokenRef` and fails closed when the reference does not resolve (the route refuses with 401/403 and logs a warning naming the field, never the value); the process-wide `META_APP_SECRET` / `META_WEBHOOK_VERIFY_TOKEN` apply only when no reference is bound (issue #10). |
| Viewer survey visibility | Viewers receive published surveys only: the list filter excludes `DRAFT` (archived drafts included, and `state=DRAFT` yields an empty page), and detail, preview, results and breakdowns of a draft answer `TENANT_RESOURCE_NOT_FOUND` so the id is not confirmed; the overview's recent list and counts apply the same predicate. Admins and Survey Managers are unaffected (issue #16). |
| Invitation deadline under the lock | `consumeInvitation`, the transaction `acceptInvitation` runs, reads the clock after acquiring the organization row lock and the invitee's user row, and uses that reading for the expiry check and `acceptedAt`, so an invitation that expires while the request waits behind a bootstrap re-run or a member change is refused (issue #21). An acceptance whose transaction reported an error but that the database shows as persisted (read after a lock on the invitation row has waited for the failed transaction to resolve) is returned as a success. An account created for a refused acceptance is kept, because removing an externally created identity cannot be made safe against a concurrent acceptance by the same person; it grants nothing without a membership, and the refusal tells the invitee that the account exists and that a fresh invitation can be accepted after signing in. |
| Consent serialization | Every consent decision (staff grant or withdrawal, STOP, participant grant, import attestation, phone-change reset) takes a row lock on the contact before event insertion and cache recomputation, so the cached status always equals the status derived from the history. Staff, STOP, participant and phone-change decisions also validate under that lock; the import path's withdrawn pre-check reads the contact before the lock, so an older import grant is still recorded but cannot outrank a later withdrawal in the derivation (latest evidence date wins). |
| Send claim and hand-off | The worker sends in two phases, both under the contact row lock shared with every consent decision. Phase 1 re-reads the message, contact, conversation and bindings, evaluates the send policy, marks the message SENDING and commits the IN_FLIGHT attempt. Phase 2 re-takes the lock, re-reads the clock (deadlines are judged as of that moment, not as of before the lock wait), re-checks the policy on the fresh contact and run, calls the provider while still holding the lock and writes the outcome in the same transaction (bounded by the provider timeout). A STOP therefore either commits before the hand-off, which suppresses the message, or waits until the provider has answered; a crash during the call leaves the committed attempt, which the next run records as UNKNOWN. |
| Edit vs launch | Draft edits run under the same survey row lock as launch, archive and test-run creation and re-read the survey there; launch and test-run creation re-read `archivedAt`, the current revision number and the revision's `updatedAt` under the lock and refuse to proceed when the survey was archived or the revision changed after it was validated. |
| Consent wording version | The notice version a participant agrees to is the one rendered in the prompt they answered: enrollments store it when the consent prompt is queued (and again on every re-prompt), a known contact's conversation stores it in `pendingContext` for typed replies while the consent prompt is open, and every minted consent button carries it in its binding payload so an older button still records the wording it was rendered with after a re-prompt. A notice change between prompt and reply therefore never claims acceptance of text the participant did not see. |
| Notice versions | Organization settings saves run under the organization row lock and bump `participantNoticeVersion` with an atomic increment only when the wording changed, so concurrent saves never share a version and every version identifies exactly one wording. |
| Delivery-state promotion | Status callbacks promote `deliveryState` with a conditional update whose WHERE clause excludes states ranked at or above the incoming status (and `FAILED` only applies below `DELIVERED`), so concurrent SENT/DELIVERED/READ callbacks can never regress the evidence. The status event row and that projection commit in one transaction: a failed projection rolls the event back, so the provider's retry of the same status is applied rather than dismissed as a duplicate, and an unmatched event is linked and applied by the sweep in one transaction too (issue #4). |
| Job lease ownership | A claim carries the lease it holds (`lease_owner`, `lease_expires_at`). Completion and failure update the job only while the row still carries that lease; otherwise the outcome is logged as `LOST` and ignored, because an expired lease may have been reclaimed by another worker (Cloud Tasks redelivery or the sweep). Lease recovery is one conditional UPDATE whose WHERE clause requires the lease to be expired at write time, so a lease renewed between the sweep's read and its write is never reset and a job is never run by two claims at once (issue #14). |
| Import resume | Every applied import row is stamped `applied_at` inside the chunk transaction that applies it. Confirming a batch left `CONFIRMED` by a crash, or marked `FAILED` by a processing error, resumes from the first unapplied row; concurrent runs of the same batch serialize on the batch row and re-read each chunk under that lock, so no row is applied twice. Only domain rules become row errors: a database error aborts the chunk, the batch is recorded `FAILED` with the partial summary (counted from the rows, so unapplied rows are in no bucket) and the request answers `IMPORT_PROCESSING_FAILED` (HTTP 500) with the batch id instead of a 200. Processing drops the raw file only; the staged rows (which carry normalized names and numbers) are deleted by the retention sweep at the end of the 24-hour staging window whatever the batch state, which bounds both the resume and the row-error report, and an expired batch reports a clear error while rows already imported are kept (issues #5, #6). The migration that adds the marker classifies rows applied before it existed by durable evidence (a completed batch processed every planned row; a created contact proves a CREATE; the contact's last import or consent evidence recorded under the batch proves an UPDATE) and turns the UPDATE rows of in-flight batches that cannot be classified into refused rows with an explanatory error, so a resume never replays stale profile values or consent evidence; the resume path applies the same CREATE/last-import rules at runtime. |
| Answers vs closure | Every answer write locks the participation and then the survey run row before re-reading the run's state and closing time, so a manual or scheduled close (which updates that row) either commits first and the answer is rejected as closed, or waits until the answer has committed. |
| Archive vs launch | Archive and launch both lock the survey row; archive re-reads the survey under the lock, refuses an active survey, cancels every scheduled live run and active test run (with their queued sends and jobs), and launch's draft guard also requires `archivedAt` to be null, so an archived survey never carries live or test outreach. |
| Imported consent dates | An attestation `collectedAt` or a row `consent_date` in the future (beyond the one-minute clock tolerance used for staff entry) is rejected at preview, and the confirmed plan is revalidated during processing, so a later STOP always outranks imported evidence. |
| Permission scopes at send time | The send policy treats the two permission scopes as independent: survey invitations and the conversation that follows them need `SURVEY_INVITATIONS`; result notices and result content need `SURVEY_RESULTS` only, so a respondent who granted results but withdrew or never granted invitations still receives the results notice, and the sharing preview's eligible count equals what is sent. Withdrawing a scope cancels only that scope's queued outreach and controls: survey invitations alone cancels every queued message about surveys (invitations, questions, acknowledgements, introductions and menus, profile offers and forms, enrollment) and their controls, leaving result notices, result content, replies about results (their dedupe keys share the `results-` prefix), View results controls and the page controls of a results menu in place; results alone cancels exactly the messages about results, replies included, and marks their recipients. Access to an already-shared snapshot follows the respondent's current results permission, which the RESULTS command checks before it lists or builds anything, every further page of its menu rechecks, and View results rechecks, so a permission withdrawn while the notice was queued and validly re-granted later restores access without another notice. A STOP withdraws every scope, cancels everything and keeps blocking both (issue #8). |
| Inbound processing under the contact lock | The processing of an inbound message from a known contact takes the contact's row lock (`lockContact`) before it reads the contact, and holds it until every reply it queues is committed; consent decisions, archive, phone changes and the hand-off to the provider take the same lock first. A withdrawal that arrives while a command is being processed therefore either commits before the permission is read (the command is answered as not permitted) or waits until the replies are queued and then cancels them and expires their controls, so a results menu can never be built on a permission read that a withdrawal invalidated before the menu was inserted. A contact whose number changed while the lock was waited for is no longer treated as the sender. The alternative, rechecking the results permission for command replies at send time, would have refused the "not available" reply that a respondent without results permission is owed, and would still have left the controls minted after the withdrawal alive (issue #8). |
| Service window moves forward only | `ConversationService.touchConversation` records a verified inbound message on the contact's conversation with a conditional update: the stored timestamp only advances, so an older event processed after a newer one (the provider delivering out of order, a backlog drained after an outage) keeps the newer timestamp and never closes a window a recent message opened. The same forward-only rule applies to the record of an enrollment in progress and to the placeholder that answers an unknown sender; the timestamp is the provider's, which the window counts from. A conditional update rather than a raw `GREATEST` keeps the statement typed; under the contact lock there is no concurrent handler to race, and the condition protects the placeholder path, which takes no lock (issue #9). |
| Reply ordering on equal timestamps | `isStaleReply` orders distinct replies by the provider timestamp first and, when it is equal (the provider stamps whole seconds), by the inbox position of each message (`InboundEvent.ingressSequence`), which also orders the messages of one webhook batch that all carry one receipt time; the receipt time remains the last resort when a side has no position. The answer keeps the position of its current revision's event (`Answer.currentIngressSequence`, backfilled by migration `20261008050000_answer_ingress_sequence` from the current revision's inbound event), so a later-arriving answer processed first is not overwritten by the earlier arrival processed second (issue #15). |
| Failure reports and later delivery evidence | A provider failure report ranks between sent and delivered in the delivery-state guard: it outranks the states that precede delivery (a message can be sent and then fail to reach the recipient, whichever order the two callbacks arrive in) and is outranked by delivered and read receipts. When such a receipt promotes a message out of the failed state, the invitation's failure mark is reverted to accepted and the message's projected error code is cleared in the same transaction, so the dispatch summary never counts one recipient as both delivered and failed, nor shows a delivered message next to a provider error, in whichever order a failure and a read receipt were applied; the append-only status events keep the failure's history (issue #19). |
| Launch retries under one idempotency key | `LaunchService.launch` looks the key up before validating, and again when anything after that lookup fails: a retry whose twin committed meanwhile (a double click racing a slow network) is refused by the state guards or the unique constraints only because the launch already happened, so it is answered with the launch's own response (the same survey detail) instead of `SURVEY_STATE_INVALID`; a different request under the same key is still `IDEMPOTENCY_CONFLICT`, and a different or missing key still meets the state guard (issue #7). |
| Test sends serialize with draft edits | `createTestRun` validates the draft, then takes the survey row lock that edits, launches and archives take, re-reads the revision under it and refuses (`SURVEY_STATE_INVALID`) when the revision changed after validation; an edit that follows a test run finds the revision referenced by a run and clones it, so a test run never references content it did not validate and a draft edit never changes a revision a run uses (issue #17). |
| Invitation acceptance waits before it judges the deadline | `consumeInvitation` takes the organization lock, upserts the invitee's user row (the second wait, held by the same identity's concurrent acceptance for another organization) and only then reads the clock for the conditional, single-use consumption of the invitation, so an invitation that expires during either wait is refused and `acceptedAt` never predates a wait (issues #21, #23). |
| Live-run slot | `SurveyRun.liveSlot` is set on the scheduled, active or closed live run of a survey and released by cancellation (unscheduling before outreach, archiving); the unique constraint on it allows at most one non-canceled live run per survey while every canceled run is retained with its frozen revision and recipient snapshot, which is what unschedule, edit and reschedule needs. `MVP.md` now states the rule this way (issue #2). |
| Readiness by purpose | `MessagingReadinessService.check` applies pure rules (`evaluateReadiness`) for a purpose: `OUTREACH` (launch, test run, activation, survey detail) needs the invitation template, the Flows the questions render with and, while profile onboarding is enabled, the `PROFILE` Flow, since first-time participants are offered it; `RESULTS` needs only the results template; `SETTINGS` reports the full picture with the results template as a warning. The live conversation additionally skips the onboarding offer, and answers the `PROFILE` command with a short reply, when the Flow is not published, so no offer dangles (issues #11, #18). |
| Revoking shared results | Revocation expires the access bindings and, in the same transaction, cancels the result notices still pending with their send jobs (`RESULTS_REVOKED`) and marks their recipients suppressed; the send policy refuses a results message whose snapshot is revoked. The hand-off of a results message holds a share lock on its snapshot row while the policy is rechecked and the provider is called, and the revocation takes the exclusive lock first, so a revocation either commits before the recheck (the notice is refused) or waits until the notice has left. Send-time outcomes (suppressed, failed, unknown) and contact-level cancellations are reflected on the result recipient rows reporting reads, and an accepted send, a retry included, makes the recipient invited again without ever moving a viewer back; a delivery failure the provider reports after acceptance stays delivery evidence on the message and does not take the respondent's access away, since the notice cannot be resent (issue #12). |
| Blocked activation | `activateRun` checks readiness before a scheduled run is committed as active. A blocked run keeps its state, records `dispatchBlockReason` plus one audit entry per reason change, and the sweep re-enqueues it every minute until messaging is repaired or the closing time passes, when it closes without sending. |
| Dashboard proxy follows the API's address | `infra/docker/nginx.conf` sets `resolver 127.0.0.11 valid=5s ipv6=off` and proxies to a variable (`set $api_upstream http://api:3000; proxy_pass $api_upstream;`), so nginx asks Docker's embedded DNS again every five seconds and the request URI still reaches the API unchanged. A name written straight into `proxy_pass` is resolved once, when nginx starts: when the API and the worker restart together Docker can hand the API the address the worker held (it allocates the lowest free one), and the dashboard then answered 502 while the API was healthy. The Docker smoke forces that swap (stop both, start the worker first). The resolver address is Docker's: the `web` image run anywhere else needs its own resolver and upstream (`DEPLOYMENT.md`). |
| The worker has no HTTP health check | The image's `HEALTHCHECK` probes the API port, which the worker never opens, so every worker container inherited a check it could not pass. The Compose worker service disables it (`healthcheck: disable: true`) instead of reporting a running worker unhealthy for its whole life; `restart: unless-stopped` covers a crashed worker, and the smoke fails if the worker is not running or is reported unhealthy. A liveness signal of the worker's own is not part of the MVP. |
| Archive takes the contact lock first | `ContactsService.archive` locks the contact row (`lockContact`) before it reads the archive state, writes it and cancels the contact's pending outreach, like consent decisions, phone changes, the processing of an inbound message and the hand-off to the provider; the archive state is the one the lock finds, so a concurrent archive that committed first is not repeated. |

## Operational choices

- **Local stack**: Docker Compose with PostgreSQL 16, the Firebase Auth emulator (auth only, no Java), API, worker, a one-shot `bootstrap` service (migrations + idempotent seed) and nginx serving the dashboard on `127.0.0.1:8080` with `/api` proxied. Loopback-only port bindings.
- **Host development**: `pnpm dev` starts the emulator, migrates, seeds, and runs API/worker/web with the Angular dev server proxying `/api`.
- **Nest decorator metadata**: operational commands (`seed`, `seed:scale`, `sweep`, `run-once`, `retention`, `bootstrap:org`) run through the built worker bundle (`scripts/run-cli.ts`) because esbuild-based runners such as `tsx` do not emit decorator metadata.
- **Database reset**: `pnpm db:reset -- --yes` refuses non-local database hosts and live/production settings. Prisma's own guard additionally blocks AI-agent invocations of `migrate reset`.
- **Cloud path (not exercised)**: Cloud Run services for API and worker, Cloud SQL, Cloud Tasks pushing to `/api/v1/internal/jobs/:id/execute` with OIDC, Cloud Scheduler calling `/api/v1/internal/sweep`. See `DEPLOYMENT.md`.
- **Flow JSON**: version 7.0 assets without `data_api_version` (no data endpoint is used). `pnpm whatsapp:validate` checks structure, dynamic references, payload keys against the inbound parser, fixtures and template specs; Meta's builder/upload validation remains authoritative.

## Execution policy for this repository

The product owner authorized, in the implementation prompt for this build, committing, pushing the feature branch, opening a pull request, replying to review comments, creating tracking issues and resolving review threads. `AGENTS.md` §2 and `START-HERE.md` record that update. Merging, force-pushing, cloud provisioning, billing, real WhatsApp sends, Meta asset changes, Terraform and CI/CD remain prohibited.
